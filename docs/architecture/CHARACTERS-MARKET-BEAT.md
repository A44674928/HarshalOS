# The Characters Market Beat — Objects, NPCs, and Items moving on a provider budget

**Status:** implemented as a read-only display layer. This document adds **no** canonical
invariant. It describes `js/characters-beat.js` (motion + budget engine),
`js/characters-cast.js` (cast and stage layout), `js/apps-characters.js` (the desktop app),
`worker/characters-beat.mjs` (the batched, cache-held read route), and
`css/characters.css`.

**Also implemented since the first revision:** a **two-lane (tiered) beat** that spends the
same calls differently — see §2b.

**One-line boundary:** market data can move a character on a stage; it cannot move
authority, money, or a decision. This is Stage 2 *Representation* in the canonical model,
exactly like the Market Context node in [`PINE-OCM-INTEGRATION.md`](PINE-OCM-INTEGRATION.md) —
the cast is a metaphor for price/volume context, not a signal, not advice, and not an
instruction.

---

## 1. The idea

The palace already renders the whole cast going about a deterministic average day
([`HARSHALS-PALACE.html`](HARSHALS-PALACE.html), regenerated by `npm run palace:build`).
The Characters app keeps the same cast and the same rings, but replaces the average day
with a **beat**: one refresh cycle at a chosen cadence. On each beat:

```text
due symbols (least-recently-refreshed, featured-weighted)
      → one provider call per symbol, held in the Worker for the beat window
      → gi-market-context-v1 packet per symbol
      → js/good-intelligence-market-context.js evaluate()   (VFI + Fibonacci bands + WaveTrend)
      → js/characters-beat.js motion()                       (mood, gait, sway, flow)
      → the stage: NPCs walk, Objects sway, Items flow
```

Three character classes, because they do not move the same way:

| Class | Behaviour | Driven by |
| :--- | :--- | :--- |
| **NPC** | Walks a berth lane: speed, stride, jitter, formation, bearing | bias vs the Fibonacci basis, realized volatility, band position |
| **Object** | Anchored at the sector's mid-arc: sways, pulses, opens an aperture | volatility (sway), energy (pulse), band break (aperture) |
| **Item** | Flows along the lane between the hub and the berth | relative volume (rate), flow direction (inbound / outbound) |

Every berth is one symbol on the reviewed Tickerbot watchlist. The cast is built from that
watchlist **at runtime** (`js/characters-cast.js`), so there is no second allowlist that
could drift from `worker/good-intelligence-tickerbot.mjs`; a test builds the whole stage
from the Worker's own exported list.

## 2. The budget: 10,000 calls per month

The reviewed plan is 10,000 provider calls per month. One symbol costs one call, so:

```text
beats per month  = (30.44 days × 1440 min) ÷ cadence
symbols per beat = floor( (budget − reserve) ÷ beats per month ), capped at 12
calls per month  = symbols per beat × beats per month
```

With the default 15% reserve (1,500 calls held back for manual refreshes and retries):

| Cadence | Beats / month | Symbols / beat (safe) | Calls / month | Share of 10,000 | Full 52-symbol sweep | Stretch (spends reserve) |
| ---: | ---: | ---: | ---: | ---: | ---: | :--- |
| 15 min | 2,922 | 2 | 5,844 | 58% | 26 beats · 6.5 h | 3/beat → 8,766 calls |
| 30 min | 1,461 | 5 | 7,305 | 73% | 11 beats · 5.5 h | 6/beat → 8,766 calls |
| **60 min** | **730** | **11** | **8,030** | **80%** | **5 beats · 5 h** | 12/beat → 8,760 calls |
| 4 h | 182 | 12 (cap) | 2,184 | 22% | 5 beats · 20 h | — |
| 1 day | 30 | 12 (cap) | 360 | 4% | 5 beats · 5 days | — |

What the table actually says:

- **A faster cadence does not refresh more characters — it refreshes fewer, more often.**
  At 15 minutes the budget affords ~3 symbols per beat, so a full sweep of 52 characters
  takes *longer* than at an hour (6.5 h vs. 5 h). Tempo and breadth trade against each other.
- **The per-beat request cap (12) binds before the budget does** at 4-hour and daily
  cadences, which is why those plans leave most of the budget unused. `npm run
  test:characters` asserts every plan stays inside the budget at every cadence.
- **The reserve stretch is offered, never assumed.** A 15-minute stretch (3/beat, 8,766
  calls) stays inside the hard 10,000 budget while eating the reserve; the app shows the
  cost before the switch is used.
- **Re-renders are free.** The Worker holds each symbol's bars for exactly one beat
  (`cadenceMinutes × 60 s`). Reloading the page, resizing, or re-opening the app inside a
  beat window answers from the isolate cache with `cacheHits` and spends nothing. A failed
  read is **not** cached, so the next beat may retry it.
- **Featured tickers cost no extra calls.** A featured symbol's age counts double in the
  rotation, so it reaches the front of the queue at half the age — roughly twice the
  refresh rate inside the same budget.

The recommendation in the UI is computed, not hard-coded: the fastest cadence whose
reserve-protected plan does not overspend the budget. At 10,000 calls and 52 berths that is
hourly (80% of budget); at 52 berths and a 15-minute cadence you get breadth-by-patience.

### Where the counts live

| Count | Where | Durable? |
| :--- | :--- | :--- |
| Calls this beat / cache hits | `worker/characters-beat.mjs` response (`data.spend`) | No — per response |
| Isolate day/month totals | module scope in the Worker | **No** — resets on redeploy, per isolate, best-effort telemetry |
| Month ledger, rotation ages, featured set | browser `localStorage` (`harshalos.characters.ledger.v1`) | Yes-ish — per browser profile; cleared with site data |
| True spend | the provider's dashboard | Yes |

Nothing in this repository claims to *enforce* the budget. The Worker caps symbols per
request and holds beats open; the browser ledger keeps the month honest; the provider
dashboard is the authority. A budget you cannot audit is a budget you will overspend.

## 2b. Two-lane (tiered) beats — the same spend, split by tempo

A single cadence forces one trade: a slow clock and everything moves rarely, or a fast clock
and only a few berths move. A tiered beat pays for a **hot lane** first (the operator's
featured tickers, refreshed every beat) and hands the remaining calls to a **sweep** that
walks the rest of the cast. The monthly cost is *identical* — `planTiers()` copies
`callsPerBeat` straight from `plan()` — only the destination of each call changes.

The planner solves for the widest hot lane that still sweeps the cast inside a target window:

```text
B = beats inside the window (e.g. 24 h)
calls_per_beat − hot ≥ (cast − hot) ÷ B          the sweep keeps up
        ⇒  hot ≤ (calls_per_beat · B − cast) ÷ (B − 1)
```

At 10,000 calls per month and 52 berths, with the 15% reserve:

| Cadence | Calls/beat | 6 h window | 12 h window | **24 h window** | 48 h window |
| :--- | ---: | :--- | :--- | :--- | :--- |
| 15 min | 2 | — | — | **1 hot + 1 sweep · 12.75 h** | 1 hot + 1 sweep · 12.75 h |
| 30 min | 5 | — | 2 hot + 3 sweep · 8.5 h | **4 hot + 1 sweep · 24 h** | 4 hot + 1 sweep · 24 h |
| 60 min | 11 | 2 hot + 9 sweep · 6 h | 7 hot + 4 sweep · 12 h | **9 hot + 2 sweep · 22 h** | 10 hot + 1 sweep · 42 h |
| 4 h | 12 | — | — | **4 hot + 8 sweep · 24 h** | 8 hot + 4 sweep · 44 h |
| 1 day | 12 | — | — | — | — |

Read the hourly row against the 15-minute row and the original question answers itself:

- **Hourly, tiered:** 9 berths refresh every hour and the whole cast still completes a sweep
  in 22 hours — the widest hot lane that keeps a daily cycle, at 80% of budget.
- **15-minute, tiered:** 1 berth moves every 15 minutes and the full cast still sweeps twice a
  day (12.75 h) — the fastest tempo the 10,000-call budget can afford, at 58% of budget.
- A plan whose hot lane would eat every call (daily cadence, for instance) is reported
  **infeasible** with the reason, not offered as a tier: it would starve the sweep and is
  just the plain rotation wearing a tier label.

Rules the tier mode keeps:

1. **A lane is a display hint.** The Worker accepts `lanes=SYM:hot,SYM:sweep`, stores the
   label per instrument, and ignores anything it does not recognize. A lane never changes
   how many calls a beat makes — it is always one call per requested symbol.
2. **Hot first, then the eldest.** `selectTieredDue()` pays the hot lane from the featured
   set (least-recently-refreshed first, so more featured tickers than the plan affords still
   rotate), then gives the remainder to the next-eldest sweep berths. The beat budget is
   never exceeded, and no berth is charged twice in one beat.
3. **Same honesty.** A hot berth without bars still freezes; a synthetic hot lane is still
   watermarked; the ledger still counts what the provider was actually asked for.

## 3. The mapping: indicator → movement

`motion()` reads the same `gi-market-analysis-v1` packet the Market Charts tab evaluates —
VFI versus its EMA reference line, the Fibonacci Bollinger basis and bands, WaveTrend with
its zones and crosses, and divergence events. Five gauges, all bounded:

| Gauge | Range | Source |
| :--- | :--- | :--- |
| `bias` | −1…1 | `(close − basis) / basis`, squashed; falls back to the 20-bar slope while bands warm up |
| `flow` | −1…1 | `VFI − EMA reference`, squashed |
| `heat` | 0…1 | `\|WaveTrend wt1\| ÷ 60` — how wound the sector is |
| `charge` | 0…1 | realized per-bar volatility against a 2% reference move |
| `crowd` | 0…1 | latest volume ÷ 20-bar mean volume |

Moods are derived in a fixed precedence, so the same packet always produces the same
word: `frozen` (no bars) → `warming-up` → `surge` / `flinch` (bullish / bearish confluence
or an extreme reversal) → `rally` / `selloff` (bias and flow agree) → `coil` (heat ≥ 0.85)
→ `churn` (charged and directionless) → `drift` / `lean-up` / `lean-down`.

Motion fields per class:

```text
npc.speed    = 0.20 + 0.55·|bias| + 0.35·charge (+0.15 if an event fired)
npc.stride   = 0.30 + 0.50·charge + 0.20·heat
npc.jitter   = charge·0.8 (+0.20 churn, +0.15 flinch)
npc.bearing  = berth angle + bias·90° + flow·~21°
npc.formation= rim (heat ≥ 0.7) | tight (crowd ≥ 0.55) | ring (flat) | column (inflow) | scatter (outflow)
object.sway  = 0.10 + 0.70·charge + 0.20·heat
object.pulse = 0.15 + 0.85·(0.15 + 0.45·speed + 0.40·heat)
object.aperture = 1 when the bar crossed a Fibonacci band, else 0.10 + 0.60·crowd
item.rate    = 0.25 + 1.50·crowd (+0.40 on rally/surge), items per beat
item.lane    = inbound (flow ≥ 0) | outbound (flow < 0)
```

The caption under the stage states the same thing in words
(`AAPL: rally · above basis · flow up · mid-band`), and the marks list carries the
indicator event labels — `bullish VFI + band confluence`, `WaveTrend bearish cross`,
`regular bearish divergence`, and an explicit `latest bar unconfirmed — held` when the
newest candle has not closed. Both the caption and the marks come from the last **closed**
bar; a pending bar can never mint a confluence event.

## 4. Honesty rules the app enforces

1. **No bars, no motion.** A berth without data freezes: zero speed, zero items, no marks,
   and a caption that says so. Nothing is interpolated, back-filled, or guessed.
2. **Synthetic never mixes with live.** The rehearsal generator
   (`CharactersBeat.rehearse`) is local, deterministic, and labeled; the app watermarks the
   canvas and the log entry, and the ledger records the beat as synthetic with 0 calls.
   Switching DATA SOURCE clears the other source's motion rather than blending it.
3. **Provenance travels with the motion.** Every directive carries `synthetic`, `source`,
   `barCount`, `status`, and the symbol, and the detail card prints them.
4. **The last closed bar, always.** The Worker requests bars with `asof`, the app displays
   the bar time, and an unconfirmed newest candle is held and labeled.
5. **No advice.** The stage footer, the directive `note`, and the app description all say
   the same thing: display-only, not investment advice, not a trade signal, and not
   permission to act. Indicator event labels are not trade instructions.
6. **Paused when hidden.** An auto-beat in a hidden tab spends nothing; it resumes and says so.

## 5. Routes and files

| Surface | Detail |
| :--- | :--- |
| `GET /api/characters/v1/beat` | `?symbols=A,B,C&interval=1h\|1d&cadence=15\|30\|60\|240\|1440[&lanes=A:hot,B:sweep]` |
| Response | `{ success, environment: "characters-beat", data: { schema: "characters-beat-v1", beatAt, interval, cadenceMinutes, holdMs, instruments[], spend } }` |
| Refusals | 400 (no symbols, over the 12-symbol cap, off-allowlist symbol, bad interval), 405 (non-GET), 503 (no `TICKERBOT_API_KEY`), 429/502/504/404 (whole-beat provider failure, with the whole-beat data attached) |
| Partial failure | 200 with per-symbol `status: "unavailable"` — a partial beat is still an honest beat |
| Worker secret | `TICKERBOT_API_KEY` (same secret the Good Intelligence Market Charts tab uses) |
| Symbols | the reviewed 52-symbol Tickerbot watchlist, imported from `worker/good-intelligence-tickerbot.mjs` — never a second list |
| Cache | per symbol + interval, TTL = the beat (`cadenceMinutes`), isolate-local |

```text
js/characters-beat.js          budget, rotation, gauges, motion, blend, ledger, rehearsal
js/characters-cast.js          cast roster, sector objects, item tokens, radial layout
js/apps-characters.js          the desktop app: canvas stage, controls, ledger, beat log
css/characters.css             app styling
worker/characters-beat.mjs     batched read route with the beat-held cache
tests/characters-beat-test.mjs engine + cast tests (budget, determinism, freeze rules)
tests/characters-beat-api-test.mjs route tests (spend discipline, refusals, no leaks)
```

## 6. What this is not

It is not a TradingView-parity implementation, a backtest, a prediction, or a live trading
surface. The JS indicators it consumes are a related port, not a line-for-line Pine runtime,
and parity is unverified ([`PINE-OCM-INTEGRATION.md`](PINE-OCM-INTEGRATION.md) §2). Motion
never enters assurance scoring, claims, the composite formula, actionability, the PLV, or
any Permit/Refuse decision. If a provider read fails, the stage freezes — that is the
correct outcome, not an error to paper over.

**Follow-ups deliberately left open:** a server-durable call ledger (D1 or KV) instead of
the isolate-local counters; a bar-for-bar parity harness against the archived Pine sources;
and per-berth cadences driven by the operator's own cast size (the tier planner already
solves for the widest hot lane, but the hot set is still nominated by hand).
